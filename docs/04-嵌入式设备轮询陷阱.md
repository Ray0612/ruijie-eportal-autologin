# 四、⭐ 坑 3：秒级轮询会压垮嵌入式设备

> 这个坑我们花了一整天排查。**症状极度误导，而且几乎查不到任何日志。**

---

## 4.1 症状

```
现象 1  路由器每隔约 6~7 分钟就重启一次
现象 2  日志里【没有任何】关机过程（不是 reboot，是硬复位）
现象 3  SSH 密码刚输完就断线（正好撞上重启）
现象 4  网络"越来越慢，最后不能用"
现象 5  重启时间点看着毫无规律
```

---

## 4.2 误导性在哪

一开始所有人（包括我）都会往这些方向想：

| 猜测 | 实际 |
|---|---|
| 内存不够 / OOM | ❌ 心跳显示一直有 60MB+ 空闲 |
| CPU 打满 | ❌ 负载 ~1.0，CPU 95% idle |
| 固件的看门狗脚本在重启 | ❌ 查了 `boot_check`、`key_services_boot_check`、`wwdog` —— 都不是 |
| 电源不稳 | ❌ 换过插座 |
| 硬件坏了 | ❌ 用户明确说"不是硬件问题" |

**为什么这么难查**：硬件看门狗复位是**静默的** —— 它不写任何日志、不走关机流程，
日志里只会看到"上一条日志"和"6 分钟后的新启动"，中间一片空白。

---

## 4.3 真正的根因

```sh
# ❌ 之前的写法
INTERVAL=30        # 每 30 秒发一次外网 HTTP 探测
                   # = 1440 次/小时
```

**在一台 ~190MB 内存、200+ 进程的嵌入式设备上，
"高频的小请求"比"低频的大请求"危险得多。**

每次 HTTP 探测意味着：
```
建 TCP 连接 → 进 conntrack 表 → NAT 记录 → 解析响应 → 销毁连接
```

1440 次/小时 ≈ 每 2.5 秒一次。再加上门户拦截时的重定向处理，
最终把系统压到某个环节卡死 ⇒ **硬件看门狗超时 ⇒ 静默复位**。

---

## 4.4 如何证明是它（可复用的排查方法）

### 方法 A：`boot_id` 计数（最有效）

每次启动，内核都会生成一个随机的 `boot_id`：

```sh
cat /proc/sys/kernel/random/boot_id
# 例：6ff93d8f-5746-44d7-ab29-0029b8b2a3da
```

**⇒ 把它记进一个持久文件，就能数出"重启了几次、每次之间隔多久"：**

```sh
LOG=/etc/storage/diag/reboots.log      # ⚠️ 放在持久分区
BID=$(cat /proc/sys/kernel/random/boot_id)
if ! grep -q "$BID" "$LOG" 2>/dev/null; then
    echo "$(date '+%Y-%m-%d %H:%M:%S')  BOOT  boot_id=$BID" >> "$LOG"
fi
```

**⇒ 实测结果：间隔稳定在 6.5 分钟 ⇒ 不是随机崩溃，是周期性的。**

### 方法 B：持久化心跳

单纯数重启还不够，要知道"断在哪一分钟"。每分钟记一行：

```sh
{
    echo "$(date '+%Y-%m-%d %H:%M:%S')  uptime=$(cut -d' ' -f1 /proc/uptime)s" \
         "load=$(cut -d' ' -f1-3 /proc/loadavg)" \
         "memfree=$(awk '/MemFree/{print $2}' /proc/meminfo)KB" \
         "procs=$(ps | wc -l)"
} >> /etc/storage/diag/heartbeat.log
```

**⇒ 一眼看出：最后一条心跳到下次启动之间空了几分钟、资源是否紧张。**

### 方法 C：单变量实验（最终定案）

```
① 停掉自动认证脚本 → 观察 20 分钟
      重启停止 ⇒ 嫌疑锁定在脚本
② 恢复脚本，但把 INTERVAL 从 30 改成 300
      重启仍然停止 ⇒ 实锤是"探测频率"
```

**我们的实测数据**：
```
INTERVAL=30    ⇒ 6.5 分钟一次重启（稳定复现）
INTERVAL=300   ⇒ 连续 1 小时以上无重启 ✅
```

---

## 4.5 ✅ 修复方案

### ① 间隔改成分钟级

```sh
INTERVAL=300          # 5 分钟
```

**安全区间参考**：

| 间隔 | 评价 |
|---|---|
| 30 秒 | ❌ **会压垮设备**（本案例实测）|
| 60 秒 | ⚠️ 短期测试可用，长期不建议 |
| 120 秒 | ✅ 可接受 |
| **300 秒** | ✅ **推荐**（掉线最多 5 分钟恢复，完全够用）|

### ② 加"零流量前置判断"

**在线时连一个包都不发：**

```sh
link_ready() {
    [ -e "/sys/class/net/$WAN_IF" ] || return 0   # 接口名不对就不拦
    st=$(cat "/sys/class/net/$WAN_IF/operstate" 2>/dev/null)
    [ "$st" = "up" ] || return 1
    grep -q "$WAN_IF" /proc/net/route 2>/dev/null || return 1
    return 0
}
```

纯读 `/sys` 和 `/proc`，**不启子进程、不发包、不记日志**。

### ③ 在线时不要写日志

```sh
if online; then
    :                      # 什么都不做，尤其不要 echo 到日志文件
else
    log "offline -> authenticate"
    ...
fi
```

**为什么重要**：每次写日志都要 `fork` 一个 `date` / `wc` / `tail` 子进程。
高频 `fork` 在嵌入式设备上是实实在在的负担。

---

## 4.6 其它"别把设备搞挂"的经验

| # | 经验 | 原因 |
|---|---|---|
| 1 | **别用 `setsid` / `nohup`，先确认固件有没有** | 很多 OpenWrt 固件精简掉了 |
| 2 | **cron 可能不支持 `@reboot`** | 只能用「每分钟检查一次」的兜底方案 |
| 3 | **脚本必须纯 ASCII** | busybox 无 locale，中文注释可能乱码成非法字节 |
| 4 | **脚本必须 LF 行尾** | CRLF 会让 `#!/bin/sh\r` 找不到解释器 |
| 5 | **日志别放 `/tmp`** | tmpfs，重启即失 |
| 6 | **持久配置放 `持久分区`** | 常见 `/etc/storage`、`/data`、`/jffs`、`/overlay`，因固件而异 |

## 4.7 排查用的诊断套件

本项目的 `router/` 目录提供了精简版：

```sh
/etc/storage/diag/reboot-watch.sh    # 每分钟采集（cron）
/etc/storage/diag/reboots.log        # 每次启动一行 ⇒ 数重启次数
/etc/storage/diag/heartbeat.log      # 每分钟 uptime/负载/内存/进程数
```

**部署**：
```bash
echo '*/1 * * * * /etc/storage/diag/reboot-watch.sh >/dev/null 2>&1' >> /etc/crontabs/root
/etc/init.d/cron restart
```

**查看**：
```sh
tail -20 /etc/storage/diag/reboots.log
tail -20 /etc/storage/diag/heartbeat.log
```

---

## 4.8 一句话总结

> **给嵌入式设备写轮询脚本，间隔要留到分钟级，不是秒级。**
> **高频小请求比低频大请求危险得多 —— 而且它挂的时候不写日志。**
