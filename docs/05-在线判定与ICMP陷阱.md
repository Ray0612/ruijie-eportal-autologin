# 五、在线判定：为什么不能只看状态码，也不能靠 ping

> 判断"当前是否已认证"，是自动重连脚本的核心。
> 判错了会造成两种严重后果：**要么永远不登录，要么疯狂登录被风控。**

---

## 5.1 推荐的判定方式

**同时满足两个条件才算"真的在线"：HTTP 状态码 = `204`，且响应体为空。**

```sh
PROBE="http://connectivitycheck.platform.hicloud.com/generate_204"
# 任何返回 204 的探测地址都可以，比如 http://www.gstatic.com/generate_204

online() {
    out=$(curl -s -m 12 -w '\n%{http_code}' "$PROBE" 2>/dev/null)
    code=$(printf '%s' "$out" | tail -n 1)     # 最后一行是状态码
    body=$(printf '%s' "$out" | sed '$d')      # 其余是响应体
    [ "$code" = "204" ] && [ -z "$body" ]
}
```

---

## 5.2 为什么必须两个条件都看

| 情况 | 状态码 | 响应体 | 正确判定 |
|---|---|---|---|
| 真的在线 | `204` | **空** | ✅ 在线 |
| 被门户劫持 | `200` | **门户的 HTML 页面** | ❌ 离线（需认证）|
| 网络完全断开 | 非 2xx / 连接失败 | — | ❌ 离线 |
| 某些 CDN/WAF 干扰 | `200` 或 `302` | 非空 | ❌ 视为未通过 |

**⚠️ 只看状态码会犯的错**：
```sh
# ❌ 这是错的！
code=$(curl -s -o /dev/null -w '%{http_code}' "$PROBE")
[ "$code" = "204" ] || [ "$code" = "200" ]      # ← 把 200 也当在线
```

**后果**：被门户劫持时返回的正是 `200` + HTML，
于是脚本认为"已在线" ⇒ **掉线了也永远不登录**。

> 我们就是这么被坑了一轮的：踢下线后脚本毫无反应，日志里一条记录都没有。

---

## 5.3 ⭐ 陷阱：不能靠 ping 判断在线

很多教程（包括一些很有名的）推荐这样：

```sh
# ❌ 很多教程这么写
ping -c 1 223.5.5.5 >/dev/null 2>&1
if [ $? -eq 0 ]; then
    echo "已连接"
else
    echo "开始认证"
fi
```

**在某些校园网里，这个方案会彻底失效。**

### 实测结论

```
设备【未认证】时：
    ping 223.5.5.5   → ✅ 通
    ping 8.8.8.8     → ✅ 通
    HTTP 探测        → ❌ 被劫持（返回 200 + 门户页面）
```

**⇒ 这个网络只拦截 HTTP/HTTPS，不拦截 ICMP。**

**⇒ 用 ping 判断 ⇒ 永远认为"在线" ⇒ 永远不登录。**

### 为什么会这样

门户的劫持通常是基于 **HTTP 层的重定向/替换**，而不是 IP 层的阻断。
ICMP 是独立协议，很多实现不会去管它。

### ✅ 正确做法

**如果确实想用 ping 做"廉价前置判断"，必须放在 HTTP 探测之前作为"快速排除"，
而不能作为"在线"的最终依据：**

```sh
online() {
    link_ready      || return 1      # ① 零流量：链路/路由
    ping_ok         && return 0      # ② ⚠️ 仅当你的网络【会】拦 ICMP 时才能这么写
    http_ok         && return 0      # ③ 兜底：HTTP 探测
    return 1
}
```

**⚠️ 但如果你的网络不拦 ICMP（像本案例），第 ② 步必须去掉**，否则永远不登录。

**⇒ 最稳妥的写法：只用 HTTP 探测（配合零流量前置判断）。**

---

## 5.4 零流量前置判断（最便宜的检查）

在发包之前，先纯读文件系统：

```sh
link_ready() {
    [ -e "/sys/class/net/$WAN_IF" ] || return 0   # 接口名不对就不拦（防误判）
    st=$(cat "/sys/class/net/$WAN_IF/operstate" 2>/dev/null)
    [ "$st" = "up" ] || return 1                  # 链路必须是 up
    grep -q "$WAN_IF" /proc/net/route 2>/dev/null || return 1   # 默认路由必须存在
    return 0
}
```

**代价：零。** 不启子进程、不发包、不写日志。

**⚠️ 注意 `[ -e "/sys/class/net/$WAN_IF" ] || return 0` 这一行**：
如果 WAN 接口名配错了（比如固件里不是 `eth4`），**不要拦截**，
让它继续走 HTTP 探测 —— 否则会误判成"永久离线"。

---

## 5.5 探测地址怎么选

| 选择 | 优点 | 缺点 |
|---|---|---|
| `http://connectivitycheck.platform.hicloud.com/generate_204` | 返回标准 204 | 依赖 DNS，且是一台厂商专用域名 |
| `http://www.gstatic.com/generate_204` | 标准 204 | 国内可能不通 |
| `http://connect.rom.miui.com/generate_204` | 小米专用 | 同上 |
| **`http://<你们学校的认证门户>/`** | 不依赖 DNS，校内可达 | ⚠️ **门户本身可能返回 200，无法区分** |

**⚠️ 关于"用门户本身当探测"**：
门户在**已认证**和**未认证**时都可能返回 200 + 页面 ⇒ **无法区分状态**。
**不建议**。

**推荐**：用一个返回 204 的公网地址 + 一个校内可达的备用地址。

---

## 5.6 探测间隔的取舍

```
间隔越短 ⇒ 掉线恢复越快，但对设备的压力越大
```

| 间隔 | 恢复延迟 | 设备压力 |
|---|---|---|
| 30 秒 | 最快 | ❌ **会压垮嵌入式设备**（见 [坑 3](04-嵌入式设备轮询陷阱.md)）|
| 60 秒 | 1 分钟内 | ⚠️ 仅建议短期调试 |
| 120 秒 | 2 分钟内 | ✅ 可接受 |
| **300 秒** | **5 分钟内** | ✅ **推荐** |

**⇒ 一般校园网会话能维持数小时，5 分钟的恢复延迟完全可接受。**

## 5.7 完整判定流程图

```
        ┌─────────────────┐
        │ link_ready()    │  纯读 /sys + /proc
        │ 接口 up? 路由在? │
        └────────┬────────┘
                 │ 否 → 离线，去登录
                 │ 是
                 ▼
        ┌─────────────────┐
        │ HTTP 探测       │  generate_204
        │ 看码 + 看响应体  │
        └────────┬────────┘
                 │
      ┌──────────┴──────────┐
      │                     │
  204 + 空体            200/其它/非空
      │                     │
      ▼                     ▼
   在线 ✅               离线 ❌
   什么都别做            去抓令牌 + 登录
```

---

## 5.8 一句话总结

> **在线判定：`204` + 空响应体，两个都要。**
> **别用 ping 当最终依据 —— 有些网络未认证时也放行 ICMP。**
